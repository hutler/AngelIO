# План разработки AngelIO

## Сценарий, вокруг которого строится плагин

Дизайнер назначает один файл двум лифтам. Каждый экземпляр имеет свой набор привязок, входные настройки и выходное состояние. Скрипт получает запрос этажа, поручает движение внешнему модулю, ждёт завершения и уведомляет остальные системы. Быстрый ответ в том же кадре и выгрузка одного из лифтов входят в основной сценарий проверки.

Из классического GSC берём читаемую последовательность действий, ожидание события конкретного отправителя и привязку времени жизни ветки к объекту. Из ActorIO — возможность проверить контракт. Из JoeIO — работу с группами размещённых объектов. Для AngelIO место, где автор читает порядок событий, — исходный файл миссии. [Скрипты карты и уведомления GSC](https://wiki.zeroy.com/index.php?title=Call_of_Duty_5%3A_Scripting_Syntax_And_Grammar)

## Границы и обмен данными

| Участник | Ответственность |
| --- | --- |
| Автор уровня | Выбирает сценарий и значения экземпляра, пишет условия и порядок событий |
| AngelScript | Хранит локальные переменные во время ожидания, вычисляет решения и публикует результат |
| Компонент Unreal | Запускает и останавливает экземпляр, передаёт типизированные значения, доставляет события подписчикам |
| Внешний игровой модуль | Реализует движение, взаимодействие, реплики или цели. Управляет временем жизни своих операций |
| MCP и командлет | Дают агенту доступ к тому же компилятору и описанию контракта, что использует runtime |

Свойство хранит значение, событие оповещает об отдельном факте. Два прибытия на один этаж дают два `Arrived`, при этом `LastFloor` одинаков. Входные значения применяются после инициализации переменных и до `Run`. Скрипт читает последующие изменения на следующем участке исполнения. У каждого экземпляра свой контекст и глобальные переменные.

## Этап 1. Исполняемый прототип

**Реализация 0.1** находится в `Plugins/AngelIO`. Обычный Win64-плагин статически связывается с AngelScript 2.39.0. Источник сценария — текстовый файл. Каждому компоненту в этой версии принадлежит своя VM. Это упрощает изоляцию и даёт эталон поведения для дальнейшей оптимизации.

В состав этапа входят `Run`, ожидание адресного события компонента, отложенная до выхода из VM рассылка событий, входные и выходные переменные трёх типов, целочисленная нагрузка события и отмена при EndPlay. Демомодуль с двумя лифтами показывает C++-интеграцию. Blueprint видит тот же компонент и делегат. MCP вызывает редакторский командлет и получает его JSON.

**Критерии приёмки.** Одна карта и один файл управляют двумя независимыми акторами. Модуль отвечает как в том же кадре, так и после движения. Уничтожение ожидающего актора исключает позднее возобновление. Ошибочный скрипт даёт диагностику через MCP. В упакованной игре доступен тот же файл миссии.

## Этап 2. Предметный API игровых модулей

**Реализовано в 0.2.** Имена `TargetName` адресуют один компонент или группу в реестре авторитетного мира. Скрипт вызывает `SendTo`; Blueprint и C++ могут также разрешить имя через `FindTargets`. Реплицируемый компонент публикует выходы и текущее ожидание. Одноразовые эффекты используют отдельный канал. Основной сетевой тест запускает listen server, обычного клиента и позднее подключение второго клиента.

Предметный API подключается через `IAngelIOScriptAPI`. Игровой модуль регистрирует в AngelScript собственные типы и команды. В демо `FindLift(name)` разрешает уникальное имя в мире миссии, а `MoveTo(floor, speed)` возвращает ссылку на отдельную поездку. Ожидание сохраняет результат при раннем завершении и возвращает `Cancelled` при уничтожении исполнителя. MCP читает объявления из того же API, который использует компилятор.

Сохранённый `Lift@` указывает на найденного актора до его уничтожения. После смены имени новый вызов `FindLift` видит нового владельца имени. Команда через сохранённую ссылку на уничтоженный актор завершает отдельную операцию с причиной `TargetGone`. Эти случаи проверяются в PIE на хосте с подключённым клиентом.

`LiftTrip.Wait(seconds)` задаёт срок ожидания в игровом времени. Значение `0` опрашивает состояние сразу. При истечении срока конкретный вызов возвращает `TimedOut`, а поездка продолжается. Несколько скриптов могут независимо дождаться той же операции. Для дальнейшего развития предусмотрены роли объектов в Details и имена в области экземпляра комнаты. Расширение типов портов включает имя, вектор и явно зарегистрированные структуры с определённым сроком жизни на границе C++.

## Этап 3. Ветки исполнения и масштаб

Стоимость запуска, память и время кадра для 1, 100 и 1000 миссий измеряет `AngelIO.Performance.WaitingMissions`. В прогоне 0.6.1 тысяча миссий добавила около 0,32 мс на кадр, а их синхронный запуск занял 484 мс. Для этого сценария оставляем существующее ожидание.

В 0.6.2 тест `AngelIO.Performance.MissionStartup` сравнил шесть пар запусков 1000 экземпляров `TimedGate.as`. В среднем создание акторов заняло 29,5 мс, регистрация базового и внешнего API со сбором объявлений — 225,5 мс, сборка модулей из исходника — 88,9 мс. При однократной компиляции и 999 загрузках байткода из памяти полное время снизилось с 507,2 до 448,6 мс. Для этой миссии постоянный кэш байткода откладываем. [Методика и результаты](AgentGuide.md#where-startup-time-goes)

В 0.6.3 одна регистрация API на 1000 независимо скомпилированных миссий сократила среднее время запуска с 488,9 до 237,6 мс в шести парных прогонах. Проверены разные этажи, счётчики поездок и места ожидания у 1000 экземпляров. На listen server инспектор показал строки 11 и 22 у разных панелей, а клиент увидел прибытие на 4-й этаж после остановки соседней миссии. С версии 0.7.0 игровые миссии по умолчанию используют общий движок авторитетного мира. Выгрузка комнаты освобождает её модули, при повторной загрузке API уже зарегистрирован. Сетевой тест меняет карту через ServerTravel, проверяет освобождение старого движка и новую поездку по запросу переподключившегося клиента. [Сравнение и команды запуска](AgentGuide.md#registering-the-api-once-for-1000-missions)

Стриминг подуровня проверяют сетевые тесты `StreamedTrips` и `WaitActor`. При удалении из мира незавершённая поездка получает `Cancelled / TargetUnloaded`. Сохранённая ссылка на лифт теряет силу при `EndPlay`, в том числе при возврате того же объекта из памяти. Постоянная миссия может вызвать `WaitActor("FreightLift", 5.0f)` до загрузки комнаты. Скрипт получает ссылку на готовый к новой поездке лифт или `null` при таймауте. После повторной загрузки тот же вызов разрешает имя заново. Состояние вызывающей миссии остаётся на её компоненте в постоянном уровне. Сохранения между мирами описаны в этапе 5.

С версии 0.6.0 миссия может запустить дочернюю функцию через `Fork`, дождаться игрового времени через `WaitSeconds` и завершить ветку по сигналу через `EndOn`. У веток собственные стеки и общие переменные миссии. В тесте `BlinkBranches` клиент видит мигание панели во время поездки и выключенную лампу после прибытия. Проверка включает выгрузку и повторную загрузку комнаты.

**Приёмка.** Две параллельные ветки завершаются предсказуемо при отмене. Повторное создание комнаты не наследует подписки предыдущего экземпляра. Выгрузка одной комнаты оставляет другую работающей.

## Этап 4. Рабочее место дизайнера и агента

Вкладка AngelIO Mission Inspector в PIE показывает файл и строку ожидания выбранной миссии и историю связанной операции. На listen server можно переключаться между лифтом и вызвавшей его панелью.

Проверка открытой карты доступна через **Tools → Validate AngelIO Missions**. Для сохранённой карты тот же валидатор вызывают `AngelIOCheck -Map=...` и MCP `validate_map`. Он проверяет скрипты, имена и типы начальных входов, прямые обращения к размещённому актору и группе по строковому литералу. Сценарии контроллера игрока также входят в проверку. Динамические имена и стриминг проверяются при исполнении.

С версии 0.4.0 в Details доступны выбор файла, входы и выходы с типами и исходными значениями, переопределение входов и подбор именованной цели в экземпляре комнаты. Дальнейшие направления редактора включают переход к строке ошибки, историю сигналов и явный перезапуск одного экземпляра после компиляции.

С версии 0.5.0 MCP возвращает акторов и компоненты сохранённой карты, их пути и привязки через `describe_scene`. Инструмент `write_script` компилирует предложенный текст, поддерживает пробный запуск и сверяет ревизию перед записью. Инструмент `read_trace` связывает вызов, ожидающий экземпляр скрипта и результат по ID операции в JSON-снимке мира. Возможное расширение — запуск сценарных тестов через MCP.

**Приёмка.** Автор или агент находит причину того, что дверь не открылась, по данным о конкретном ожидании, отправителе и получателе. Один и тот же сценарий проверяется в CI и через MCP с одинаковой диагностикой.

## Этап 5. Сохранения и выпуск

Сервер сохраняет именованный этап и его версию на диск отдельно для карты, экземпляра комнаты, компонента и файла скрипта. После загрузки комнаты или перезапуска сервера новый `Run()` читает этап через `LoadCheckpoint`, восстанавливает ожидание и публикует состояние клиентам. Миссия `Examples/RoomDelivery.as` сохраняет `Dispatched` перед поездкой, чтобы повторить её при перезапуске в пути, `Delivered` после прибытия лифта и `Complete` после принятия доставки. Сетевые тесты охватывают повторную загрузку, отдельную копию комнаты, позднее подключение и восстановление из того же слота после перезапуска.

В 0.6.1 проверены выгрузка и возврат ячейки World Partition, позднее подключение к восстановленной миссии и запуск упакованных Win64 Development и Shipping. Оба собранных приложения выполнили демомиссии и записали прибытия в новый слот. [Воспроизвести проверки](AgentGuide.md#win64-release-and-scaling-checks)

**Приёмка.** Сохранение во время поездки восстанавливает один результат. Повторное открытие карты и повторная загрузка не дублируют подписки или одноразовые действия. Карта проходит ту же проверку на целевой платформе.
